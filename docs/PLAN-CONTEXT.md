# 设计方案：对话记忆 → 上下文管理（Context Management）

> 目标：把现在「超过 N 轮就压成 300 字摘要」的对话记忆，升级成**按 token 预算管理上下文**的正式功能。
> 状态：待评审，未开工。所有结论都基于当前仓库代码（1.0.13 + C2/A6 修复）。

---

## 0. 现状（读代码得出的事实）

| 现状 | 位置 | 问题 |
|---|---|---|
| 按**轮数**取历史：`historyStore.recent(historyTurns)` | `pipeline.ts:462` | 滑动窗口：窗口满了之后每轮都会移出最老一条 → 前缀内容每轮都变 → **prompt cache 几乎全 miss** |
| 按**轮数**触发压缩：`count() >= turns*2` 就把**全部**历史压掉，只留摘要 | `pipeline.ts:810`、`drop()` | 压缩后一轮都不留，模型突然丢失最近细节；且压缩无水位概念，触发频繁 |
| 摘要写死 1200 字上限 + 提示词要求"不要分点、300 字以内" | `summarizer.ts` | 丢具体信息（数字、路径、结论、待办） |
| 专用总结模型（Base URL / Key / 模型） | `types.ts:summary`、`ModelPane.tsx:317` | 要维护三套凭据，用户基本不开 |
| **Agent 路径完全不带摘要**，且历史硬编码 6 轮 | `runner.ts:132` | 同一份上下文，两条链路口径不一致 |
| 压缩时 `historyStore.drop()` 直接删消息 | `pipeline.ts:832` | 本地记录被销毁，压缩不可回退 |
| 历史里不含图片（只存文字） | `historyStore.add` | ✅ 这点是对的，继续保持 |

## 1. 核心决策（先看这 6 条，其余都是细节）

1. **预算制替代轮数制**：一切按 token 算，不按轮数算。`llm.historyTurns` 退役。
2. **压缩水位 + 滞回**，替代滑动窗口：涨到预算 85% 才压，一次压到 ~45%，之后重新稳定。
   → 这是缓存命中率的关键（见 §4），比任何"注入技巧"都重要。
3. **三挡 = 预算的三等分点**：低 1/3、中 2/3、高 = 模型可用上限（上限要扣输出预留，见 §2 的说明）。
4. **压缩一律用主模型**，删掉专用总结模型整套配置（含 `llm.summary.apiKey` 这条 secret）。
5. **压缩是"重写摘要"，不是"删消息"**：原文留在本地记录里，只前进一个归档游标。
6. **聊天和 Agent 共用同一个上下文组装器**（`planContext`），不再各写一套。

## 2. 预算计算

### 2.1 模型窗口从哪来

`/v1/models` 只返回 id，**不返回上下文长度**，所以按优先级猜：

```
1. 用户手动指定  settings.context.modelWindow   （0 = 自动）
2. 内置模型表    按 model 名正则匹配（deepseek / gpt / claude / doubao / qwen / kimi / glm …）
3. 兜底          128k，并在 UI 上标注"按 128k 估算，可手动改"
```

内置表放在 `src/shared/model-window.ts`，只作**保守估计**用途；表过期不会导致功能坏掉（用户可覆盖）。

### 2.2 三挡数值

```
window        = 模型窗口（如 128000）
reservedOut   = min(8192, window * 0.15)      // 给回答 + 工具循环留的空间
usable        = window - reservedOut - 4096   // 再留 4k 估算误差缓冲
high          = usable
mid           = round(usable * 2 / 3)
low           = round(usable * 1 / 3)
```

128k 的模型 → 高 116k / 中 77k / 低 39k。UI 里直接显示这三个数。

> ⚠️ 需要你拍板：**"高"不能字面等于 window**。真按 100% 填满，模型必然报
> `context_length_exceeded`（因为还要生成本轮回答）。方案里"高"= 可用上限 ≈ window 的 90%。
> 如果你要的是"贴着 window 的数字显示"，我可以显示 window，但实际按 usable 截断——建议不要这么做，容易误导。

### 2.3 token 估算（要准，不然水位没意义）

```
estimateTokens(text) = cjkChars * 1.0 + otherChars / 3.5
estimateTokens(messages) = Σ 上面 + 每条 4 token 结构开销 + 图片固定 1200（1280×800 截图实测区间）
```

**校准**：每次请求后拿 `usage.prompt_tokens` 反推系数（EWMA，α=0.3），下一轮用校准后的系数。
所以第一轮可能偏保守，三轮后基本贴合真实值。估算只用于"提前判断"，真实值以 usage 为准。

## 3. 压缩策略

### 3.1 触发与目标

```
每轮请求前：
  used = 估算(system + 摘要 + 历史 + 本轮输入 + 图片)
  if used > budget * 0.85        → 需要压缩
     压到 budget * 0.45 以下    → 一次压够，避免频繁触发
  if 触发后仍压不下去（单轮输入就超）→ 降级：截断该轮输入并提示用户
```

- **保留最近窗口**：从最新往前累计，至少保留最近 2 轮原文，最多保留到预算的 30%。
  超出部分才进压缩。
- 压缩输入 = 旧摘要 + 待归档消息（和现在一样递归滚动）。
- 压缩输出 = 新摘要（覆盖旧的），并推进 `archivedUpTo` 游标。

### 3.2 摘要字数（按档位放宽）

| 档位 | 硬上限 | 目标 |
|---|---|---|
| 低 | 1800 字 | 只留主干 |
| 中 | 3000 字 | 主干 + 具体结论 |
| 高 | 4500 字 | 尽量完整，接近"会议纪要"密度 |

按 token 折算占比约 4~6% 预算，不会反噬上下文。

### 3.3 摘要提示词改造（保留"有人味"，但强制留具体信息）

现有提示词的优点：第三人称叙事、有情绪和偏好、不罗列。**保留**。
要改的两点：

1. 删掉"300 字以内""不要分点"的硬约束，改成"按档位字数上限，宁可长一点也要把事说清楚"。
2. 增加必须保留清单（写进提示词，作为硬要求）：
   - 称呼、身份、明确说过的偏好与雷区
   - 正在做的事 + 进度 + 卡在哪
   - 已做的**决定**和**结论**（不要只写"讨论过 X"）
   - 具体数字、文件名、路径、命令、报错原文（这些最容易被压没）
   - 未完成的待办与承诺
3. 结构：`叙事段落` + `【关键事实】` 短列表（允许分点，仅这一节）。叙事负责"人味"，列表负责"可检索"。

## 4. 缓存命中规则（这是本次改动的重心）

### 4.1 原理

OpenAI 兼容接口（OpenAI / DeepSeek / 方舟 / Kimi …）都是**前缀缓存**：
请求的 message 数组从头开始逐 token 比对，命中到第一个不一致处为止。
所以规则只有一条内核：**前缀必须逐字节稳定，只在尾部追加。**

### 4.2 具体规则

| # | 规则 | 说明 |
|---|---|---|
| R1 | 固定顺序 `[system] [历史…] [本轮 user(+image)]` | 摘要拼在 system 尾部，**不**单独插在中间 |
| R2 | 历史**只追加不修改** | 禁止"每轮删最老一条"的滑动窗口（现状正是这么干的） |
| R3 | system 里禁止动态内容 | 不许放时间戳、"第 N 轮"、token 数、随机 id。现在 `补充：你的名字是「X」` 只在改名时变，可接受 |
| R4 | 图片只在最后一轮 | 历史里存 `[屏幕截图]` 占位；现状已经这样，保持 |
| R5 | 压缩是**唯一**允许改前缀的操作 | 且一次压够（滞回），压缩后立刻稳定 |
| R6 | 工具循环（Agent）只追加 | 同一轮内的 tool_calls / tool 结果按顺序 append，不动前面 |

### 4.3 效果对比

```
现状（滑动窗口，8 轮）：
  第9轮   [sys][1..8][9]        ← 命中 sys
  第10轮  [sys][2..9][10]       ← 前缀从第 2 条就变了 → 命中只有 sys
  → 稳定命中率 ≈ system 占比，通常 10~20%

新方案（水位+滞回，预算 77k）：
  第1..40 轮  [sys][summary][1..N][新]   ← 前缀完全不变 → 命中率随时间逼近 95%+
  第41轮     触发压缩 → [sys][summary'][k..N][新]  ← 这一次 miss（不可避免）
  第42..80 轮 重新稳定
```

### 4.4 可观测指标

`streamChat` 已经把 `usage` 取回来了，扩一个字段即可：
- OpenAI：`usage.prompt_tokens_details.cached_tokens`
- DeepSeek：`usage.prompt_cache_hit_tokens`
- 其他：没有就显示"—"

设置页显示"最近一次：命中 87%（12.1k / 13.9k）"。这样"缓存友好"不是口号，是可验证的。
**验收测试**也用这个：mock 服务端记录每次请求的 messages，断言第 N 轮和第 N+1 轮的前缀哈希一致。

## 5. 注入方式

单条 system 拼接（兼容只接受一个 system 的服务端），顺序固定：

```
<用户自定义 systemPrompt>
<可选：你的名字是「X」>
【更早的对话摘要】
<summary>
（以下为最近对话原文）
```

- 摘要为空时整段不出现（不留空标题）。
- 摘要变化只发生在压缩时 → 不影响轮间缓存。
- 不给摘要加"生成时间"，避免无意义的时间戳污染前缀（想显示时间就放到 UI 里）。

## 5.1 时间感知（时间戳注入）

### 5.1.1 结论

**可以做，而且推荐做**——它恰好是缓存安全的：**历史消息的时间戳在写入时冻结**，
之后每一轮发出去都是同一串字节，前缀不变；**只有"当前消息"的时间是每轮新算的，而它永远在最末尾**。

### 5.1.2 三条铁律

| # | 规则 | 为什么 |
|---|---|---|
| T1 | 历史消息用**绝对时间**并冻结，禁止"3 分钟前"这类相对描述 | 相对时间必须每轮重算，一旦重算前缀就变 → 缓存全废；而且冻结的相对时间过几天就是错的（"3 分钟前"读到的是三天前的消息） |
| T2 | 当前时间只注入**最后一条消息**，且放在**正文之后** | 尾部追加不影响前缀命中 |
| T3 | system 里只写**静态**的时间使用说明，绝不写"当前时间：…" | 写进 system = 每轮变 = 每一轮都全量 miss（这条和 R3 是同一条底线） |

### 5.1.3 具体格式

```
历史消息（冻结，`history.json` 里本来就有 at 字段，不用改存储）：
  [11-20 14:32] 用户：帮我把那个 demo 打包一下
  [11-20 14:33] 助手：打好了，在 release/ 下

当前这条消息（请求时计算，追加在末尾）：
  你说的这段话……
  [现在 11-20 12:32 周五 · 距上一条 2 小时]

system 里固定一句（内容永不变）：
  消息前的 [MM-DD HH:mm] 是发生时间，只用来判断先后与间隔；不要主动报时。
```

- **格式必须手写拼**，不能用 `toLocaleString()`：它受系统 locale 影响（本机是 `2026/11/20 12:32:23`），
  换机器/换语言就变字节 → 前缀立刻失效。统一 `MM-DD HH:mm`，跨年时补成 `YYYY-MM-DD HH:mm`。
- token 成本：每条约 8 token，40 条历史 ≈ 320 token，占中档预算 0.4%，可接受。
- 只在"距上一条超过 5 分钟"时才对当前消息附带相对间隔，避免每轮都写"距上一条 3 秒"这种噪音。

### 5.1.4 连带要改的两处

1. **摘要也要吃时间**：现在 `summarizer.ts` 只拼 `角色：内容`，摘要天然丢时间线。
   改成 `[11-20 14:32] 用户：…`，并在摘要提示词里要求保留"昨天/上周三"这类相对锚点 + 关键日期。
2. **时间感知的副作用**：模型容易变成"报时器"（"现在 12:32 了，该吃饭了"）。
   在 system 那句说明里明确"不要主动报时"，只用于理解先后关系。

### 5.1.5 可选粒度（做成设置项，见 §7）

- `off`：不带任何时间（最省 token，适合纯闲聊）
- `current`：只给当前消息带时间与间隔（默认，够用且几乎零成本）
- `full`：每条历史都带（模型对"什么时候发生的"最敏感，约 +8 token/条）

## 7. 设置页 UI 与「可动设置」全清单

新增独立 tab「上下文」（放在「大模型」之后），替代现在 `ModelPane` 里的「对话记忆」区块。

### 7.1 可动设置（共 6 项 + 4 个按钮）

| # | 设置 | 形态 | 默认 | 说明 |
|---|---|---|---|---|
| 1 | 启用上下文 | 开关 | 开 | 关 = 单轮对话，不压缩、不带历史（对应旧 `historyTurns=0`） |
| 2 | 长度档位 | 三选一：低 / 中 / 高 | 中 | 直接显示换算后的 token 数，如 `低 39k / 中 77k / 高 116k` |
| 3 | 模型窗口 | 自动识别值 + 「手动指定」展开 | 自动 | 自动 = 内置表 + 兜底 128k；手动填了就以手动为准 |
| 4 | 时间感知 | 三选一：关闭 / 仅当前消息 / 每条消息 | 仅当前消息 | 见 §5.1.5。UI 上标注"每条消息"会多花约 8 token/条 |
| 5 | 保留最近原文 | 数字 1–8 轮 | 4 轮 | 压缩时这几轮不进摘要、逐字保留。设太小 → 细节丢；太大 → 压缩收益低 |
| 6 | 摘要字数上限 | 「跟随档位 / 手动」 | 跟随档位 | 跟随 = 1800/3000/4500 字；手动才出输入框 |

按钮（不是设置项，但属于该页操作）：`立即压缩`、`查看摘要`、`刷新`、`清空上下文`。

#### 「保留最近原文」到底在说什么

它**不是**"模型只能看到最近 N 轮"（模型永远能看到全部：摘要 + 全部未压缩原文），
它决定的是**压缩发生时，哪些内容以原文形式留下、哪些被揉进摘要**。

现在的代码是压缩时 `drop()` 掉**全部**历史，一条不留 —— 所以压缩完模型会突然"忘了刚说的话"，
用户说"就刚才那个"它就接不上。这个参数就是修这个。

```
20 轮对话，保留最近 4 轮：
  第 1–16 轮  → 揉进摘要（细节会损失，但省空间）
  第 17–20 轮 → 原封不动发给模型（一个字不改）
```

| 取值 | 效果 | 适合 |
|---|---|---|
| 1 | 只留最后一轮，上一轮说过的事可能已经被压成摘要 | 极度省 token |
| 4（默认） | 最近两三个来回的措辞、指代、语气都还在 | 语音陪伴的常态 |
| 8 | 细节保真最高，但压缩腾出的空间少，压缩会更频繁 | 长任务 / 连续操作 |

代价是明确的：留得越多，压缩后省下的空间越少；留得越少，越容易丢掉"刚才那句话"的细节。

### 7.2 只读信息（给用户判断依据）

- 当前占用：`12.4k / 77k (16%)` + 进度条（<70% 绿 / 70–85% 黄 / >85% 红）
- 模型窗口来源：自动识别 / 手动指定 / 兜底 128k —— 明确告诉用户这个数是怎么来的
- 摘要：字数、更新时间、已归档条数、累计压缩次数
- 最近一次缓存命中：`87%（12.1k / 13.9k）`，服务端不返回就显示"—"
- 上次压缩前后：`压缩前 71k → 压缩后 34k`

### 7.3 刻意**不**暴露（写成常量，不给开关）

| 内部常量 | 原因 |
|---|---|
| 触发水位 85% / 目标 45% | 让用户调到 99% 会变成"每轮都压缩"，既慢又摧毁缓存；这是工程判断，不该交给用户 |
| 输出预留 `min(8192, 15%)` 与 4k 缓冲 | 调小直接导致 `context_length_exceeded` |
| token 估算系数 | 已用 `usage` 自动校准，暴露只会让人调坏 |
| 缓存规则 R1–R6 | 这是实现契约，不是偏好 |

> 如果以后确实收到"我要更早/更晚压缩"的反馈，再考虑单独加一个「压缩积极度」三挡
> （对应 85/45、75/40、92/50），而不是直接暴露百分比。

## 9. 风险与取舍

| 风险 | 处理 |
|---|---|
| 模型窗口猜错 | 保守兜底 + 手动覆盖 + 水位只算 85%；真超长时捕获 `context_length_exceeded` → 强制压缩并重试一次 |
| 估算偏差累积 | 用 `usage.prompt_tokens` 每轮校准，水位和缓冲双保险 |
| 压缩本身要花一次请求 | 用主模型、`temperature 0.2`、45s 超时；放在回答播报期间做，用户无感；下一轮若仍在压则等它（有超时兜底） |
| 摘要越滚越长 | 每次是"重写"不是"追加"，硬上限按档位；实测超出就二次压 |
| 高档太贵/太慢 | 默认 mid；UI 里标注高档的代价 |
| 删掉专用总结模型会让某些用户成本上升 | 摘要调用占比很低（每压缩一次 1 次请求）；用量页仍单列 `summary`，可观测 |

## 10. 需要你拍板

1. **「高」= window 还是 window 扣掉预留？** 我建议扣（显示上写"可用上限"），否则必炸。
2. **默认档位**：建议 `中`。低档适合长期挂着聊天，高档适合真要它记住细节。
3. **设置页形态**：新增独立「上下文」tab（8 个 tab），还是继续塞在「大模型」页里？我倾向独立 tab。

## 12. 实施记录（2026-11-20 已完成，未打包）

按评审意见做的四处调整，**与上文方案不同，以本节为准**：

| 方案原文 | 实际实现 | 原因 |
|---|---|---|
| `context.enabled` 总开关 | **删除**，上下文永远开启 | 上下文是底层能力，不该在 UI 上被关掉 |
| 摘要字数上限（跟随/手动） | **删除设置项**，永远跟随档位（1800/3000/4500） | 少一个旋钮，避免用户把摘要调到没有信息量 |
| 「查看摘要」按钮 | **删除**，只显示字数/更新时间/归档条数/压缩次数/前后体积 | 摘要可能几万字，展示没有意义 |
| 「保留最近原文」 | 改名 **「压缩保留对话轮数」** | 原名看不出它只影响压缩时的保真度 |

压缩时机按**阻塞方案**实现：回答结束后若超 85% 水位就在后台压，下一轮开始前 `await` 它（`settleContext`），
既不会让用户干等，也不会带着过期摘要重复压。

最终设置项（与本文件 §7.1 的旧表相比，只剩 4 项）：

| 设置 | 形态 | 默认 |
|---|---|---|
| 长度 | 低 / 中 / 高 | 中 |
| 模型窗口 | 自动识别 + 手动指定（0 = 自动） | 0 |
| 时间感知 | 关闭 / 仅当前消息 / 每条消息 | 仅当前消息 |
| 压缩保留对话轮数 | 1–12 | 4 |

按钮：刷新 / 立即压缩 / 清空上下文。

实测（E2E `context-compact-test.mjs`，本地假 SSE 服务端）：5 轮对话后自动压缩 1 次，
8 条消息并入摘要，估算 3274 → 872 tokens，下一轮请求里确实出现 `【更早的对话摘要】`。
